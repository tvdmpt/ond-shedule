# Смены — Telegram Mini App

## Дополнения к существующему проекту

Изменения внесены в текущую структуру проекта; новый проект не создавался.

- В таблице графика заголовок первого столбца — **«Сотрудник»**. Таблица содержит ровно восемь столбцов: `Сотрудник | ПН | ВТ | СР | ЧТ | ПТ | СБ | ВС`.
- Потребности разделяются на обязательные и желательные. Дополнительная потребность ВК01 на 11:00–15:00 задана как желательная только с понедельника по пятницу.
- Покрытие рассчитывается по временным сегментам, а не только по факту пересечения смены с интервалом. Желательная потребность показывает только дополнительное покрытие сверх обязательного минимума.
- Нехватка желательного покрытия отображается как информационное сообщение и не блокирует публикацию. Нехватка обязательного покрытия по-прежнему требует явного подтверждения.
- В форме смены можно отметить подменного сотрудника и выбрать исходную территорию. Смена учитывается в покрытии целевой территории. Пересечение смен одного сотрудника на разных территориях блокируется в интерфейсе.
- SQL-схема расширена полями `is_substitute` и `substitute_from_location_id`. Добавлено ограничение PostgreSQL, запрещающее пересекающиеся смены одного сотрудника.

## Установка

Требуется Node.js LTS.

```bash
npm install
cp .env.example .env.local
npm run dev
```

Для PowerShell вместо `cp` можно использовать:

```powershell
Copy-Item .env.example .env.local
```

## Применение схемы Supabase

Для новой базы выполните `supabase/schema.sql` в SQL Editor Supabase.

Для уже существующей базы выполните миграцию:

`supabase/migrations/20261029_schedule_substitutions.sql`

Миграция добавляет поля подмены и ограничение от пересечения смен. Если в существующих данных уже есть пересекающиеся смены одного сотрудника, перед применением ограничения их нужно исправить.

## Ограничения текущей версии

Сейчас проект остаётся демонстрационным: данные интерфейса хранятся в состоянии React, а форма входа допускает локальный выбор сотрудника в демо-режиме. Хотя SQL-схема подготовлена для хранения подмен и PostgreSQL ограничивает пересечения, сквозная запись смен и потребностей из интерфейса в Supabase ещё не подключена. Для рабочей эксплуатации необходимо завершить серверную авторизацию, маппинг сотрудников и локаций на UUID из базы и операции записи через Supabase с RLS. Не используйте демо-вход для реальных персональных данных.


## Обновление таблицы локаций и статуса подмены

- В менеджерской таблице нажмите кнопку с тремя точками и выберите `ВК01`, `ВК03` или `ЗИЛ`. Таблица показывает смены только выбранной локации, в ячейках — время смены сотрудника.
- Последняя строка `ПОДМЕНА` содержит статус по каждому дню. Нажмите `✕ Нет`, чтобы отметить, что подмена не найдена, или `✓ Есть`, если подмена найдена. Статусы сохраняются в локальном хранилище браузера этого устройства. Для общего статуса между менеджерами потребуется подключить его к Supabase.
- Начальные обязательные потребности: ВК01 — два сотрудника с 07:00 до 15:00 в будни и один с 07:00 до 15:00 в выходные; с 15:00 до 22:00 нужен один сотрудник ежедневно. Дополнительно на ВК01 в будни с 11:00 до 15:00 желательно ещё два сотрудника. ВК03 и ЗИЛ — по одному сотруднику с 07:00 до 22:00 ежедневно.
- Если смена назначена на другую территорию как подмена, она учитывается в покрытии целевой локации; пересечение смен одного сотрудника не допускается.

### Автоматический статус «ПОДМЕНА»

В строке «ПОДМЕНА» таблицы статус больше не переключается вручную. Для каждой выбранной локации и дня приложение проверяет обязательное покрытие на всём промежутке 07:00–22:00, разбивая его на временные сегменты по границам потребностей и смен:

- `✓ Не нужна` — обязательная потребность закрыта обычными назначениями;
- `✓ Найдена` — обязательная потребность закрыта, и на локацию назначена подмена;
- `✕ Нужна` — есть незакрытый обязательный интервал и подмена не назначена;
- `✕ Не закрыто` — подмена назначена, но обязательное покрытие всё ещё неполное.

Желательная потребность ВК01 с 11:00 до 15:00 не влияет на этот статус. ВК01 использует минимум 2 человека 07:00–15:00 в будни и 1 в выходные, плюс 1 человека 15:00–22:00 ежедневно. ВК03 и ЗИЛ требуют по 1 человеку 07:00–22:00 ежедневно.

Проверка выполняется по текущим сменам в состоянии приложения. Для совместного статуса между устройствами и постоянного сохранения назначений требуется завершить запись/чтение смен через Supabase; демо-режим хранит смены только в состоянии текущего сеанса.
