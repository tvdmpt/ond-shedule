# Смены — Telegram Mini App

## Дополнения к существующему проекту

Изменения внесены в текущую структуру проекта; новый проект не создавался.

- В таблице графика заголовок первого столбца — **«Сотрудник»**. Таблица содержит ровно восемь столбцов: `Сотрудник | ПН | ВТ | СР | ЧТ | ПТ | СБ | ВС`.
- Потребности разделяются на обязательные и желательные. Дополнительная потребность ВК01 на 11:00–15:00 задана как желательная только с понедельника по пятницу.
- Покрытие рассчитывается по временным сегментам, а не только по факту пересечения смены с интервалом. Желательная потребность показывает только дополнительное покрытие сверх обязательного минимума.
- Нехватка желательного покрытия отображается как информационное сообщение и не блокирует публикацию. Нехватка обязательного покрытия по-прежнему требует явного подтверждения.
- В форме смены можно отметить подменного сотрудника и выбрать исходную территорию. Смена учитывается в покрытии целевой территории. Пересечение смен одного сотрудника на разных территориях блокируется в интерфейсе.
- SQL-схема расширена полями `is_substitute` и `substitute_from_location_id`. Добавлено ограничение PostgreSQL, запрещающее пересекающиеся смены одного сотрудника.

## Установка

Требуется Node.js LTS.

```bash
npm install
cp .env.example .env.local
npm run dev
```

Для PowerShell вместо `cp` можно использовать:

```powershell
Copy-Item .env.example .env.local
```

## Применение схемы Supabase

Для новой базы выполните `supabase/schema.sql` в SQL Editor Supabase.

Для уже существующей базы выполните миграцию:

`supabase/migrations/20261029_schedule_substitutions.sql`

Миграция добавляет поля подмены и ограничение от пересечения смен. Если в существующих данных уже есть пересекающиеся смены одного сотрудника, перед применением ограничения их нужно исправить.

## Ограничения текущей версии

Сейчас проект остаётся демонстрационным: данные интерфейса хранятся в состоянии React, а форма входа допускает локальный выбор сотрудника в демо-режиме. Хотя SQL-схема подготовлена для хранения подмен и PostgreSQL ограничивает пересечения, сквозная запись смен и потребностей из интерфейса в Supabase ещё не подключена. Для рабочей эксплуатации необходимо завершить серверную авторизацию, маппинг сотрудников и локаций на UUID из базы и операции записи через Supabase с RLS. Не используйте демо-вход для реальных персональных данных.


## Обновление таблицы локаций и статуса подмены

- В менеджерской таблице нажмите кнопку с тремя точками и выберите `ВК01`, `ВК03` или `ЗИЛ`. Таблица показывает смены только выбранной локации, в ячейках — время смены сотрудника.
- Последняя строка `ПОДМЕНА` содержит статус по каждому дню. Нажмите `✕ Нет`, чтобы отметить, что подмена не найдена, или `✓ Есть`, если подмена найдена. Статусы сохраняются в локальном хранилище браузера этого устройства. Для общего статуса между менеджерами потребуется подключить его к Supabase.
- Начальные обязательные потребности: ВК01 — два сотрудника с 07:00 до 15:00 в будни и один с 07:00 до 15:00 в выходные; с 15:00 до 22:00 нужен один сотрудник ежедневно. Дополнительно на ВК01 в будни с 11:00 до 15:00 желательно ещё два сотрудника. ВК03 и ЗИЛ — по одному сотруднику с 07:00 до 22:00 ежедневно.
- Если смена назначена на другую территорию как подмена, она учитывается в покрытии целевой локации; пересечение смен одного сотрудника не допускается.

### Автоматический статус «ПОДМЕНА»

В строке «ПОДМЕНА» таблицы статус больше не переключается вручную. Для каждой выбранной локации и дня приложение проверяет обязательное покрытие на всём промежутке 07:00–22:00, разбивая его на временные сегменты по границам потребностей и смен:

- `✓ Не нужна` — обязательная потребность закрыта обычными назначениями;
- `✓ Найдена` — обязательная потребность закрыта, и на локацию назначена подмена;
- `✕ Нужна` — есть незакрытый обязательный интервал и подмена не назначена;
- `✕ Не закрыто` — подмена назначена, но обязательное покрытие всё ещё неполное.

Желательная потребность ВК01 с 11:00 до 15:00 не влияет на этот статус. ВК01 использует минимум 2 человека 07:00–15:00 в будни и 1 в выходные, плюс 1 человека 15:00–22:00 ежедневно. ВК03 и ЗИЛ требуют по 1 человеку 07:00–22:00 ежедневно.

Проверка выполняется по текущим сменам в состоянии приложения. Для совместного статуса между устройствами и постоянного сохранения назначений требуется завершить запись/чтение смен через Supabase; демо-режим хранит смены только в состоянии текущего сеанса.

## Отправка пожеланий менеджерам в личные сообщения Telegram

Таблица графика и её дизайн не меняются. Основной сценарий сотрудника — выбрать дни и интервалы доступности, сохранить пожелания; после сохранения серверная функция отправляет сообщение всем настроенным менеджерам в Telegram.

1. Создайте Telegram-бота через `@BotFather` и задайте серверный secret `TELEGRAM_BOT_TOKEN` в Supabase Edge Functions. Не добавляйте токен в `VITE_` переменные и клиентский код.
2. Каждый менеджер должен открыть бота в Telegram и нажать **Start**. Telegram не разрешает боту первым начинать личную переписку.
3. Получите Telegram chat ID каждого менеджера и задайте secret `TELEGRAM_MANAGER_CHAT_IDS` как список ID через запятую, например `123456789,987654321` (используйте реальные ID, не пример).
4. В `employees` привяжите Telegram ID сотрудников к записям `telegram_user_id`. Имя сотрудника для уведомления берётся из проверенной записи базы, а не из клиентского запроса.
5. Разверните функцию `availability-notify` в Supabase. Требуются secrets `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`, а также `TELEGRAM_BOT_TOKEN` и `TELEGRAM_MANAGER_CHAT_IDS`.
6. Откройте Mini App через кнопку Telegram-бота. В обычном браузере пожелания сохраняются только локально и уведомление не отправляется.

Пример команд Supabase CLI из корня проекта:

```bash
supabase functions deploy availability-notify --no-verify-jwt
supabase secrets set TELEGRAM_BOT_TOKEN=ВАШ_ТОКЕН
supabase secrets set TELEGRAM_MANAGER_CHAT_IDS=ID_МЕНЕДЖЕРА_1,ID_МЕНЕДЖЕРА_2,ID_МЕНЕДЖЕРА_3
```

Также проверьте, что настроены `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` как secrets проекта. Функция самостоятельно проверяет Telegram `initData` и сверяет Telegram ID с записью сотрудника в базе. Если Telegram не доставил сообщение хотя бы одному менеджеру, интерфейс не заявляет об успешной отправке всем; в ответе функции возвращается число успешных и неудачных доставок.

**Важно:** менеджеры получат пожелания в личные сообщения, но это уведомление само по себе не делает локальное состояние интерфейса постоянной базой заявок. Для общего списка заявок на всех устройствах необходимо отдельно завершить сохранение `availability_requests` и `availability_intervals` в Supabase.

## Упрощённый Telegram-бот для пожеланий по сменам

В проект добавлена отдельная Supabase Edge Function `shift-bot`. Она работает как Telegram-бот: сотрудники подают пожелания в переписке с ботом, а подключённые менеджеры получают каждую заявку в личные сообщения. Таблица графика и её дизайн не меняются.

### 1. Примените миграцию

В Supabase SQL Editor выполните файл `supabase/migrations/20261029_shift_bot.sql`. Он создаёт таблицы состояния диалога и подписок менеджеров. Существующие таблицы `employees`, `availability_requests` и `availability_intervals` используются повторно.

### 2. Укажите секреты и список менеджеров

Создайте бота через `@BotFather`, затем в терминале из корня проекта выполните:

```bash
supabase secrets set TELEGRAM_BOT_TOKEN=ВАШ_ТОКЕН
supabase secrets set TELEGRAM_MANAGER_IDS=TELEGRAM_ID_МЕНЕДЖЕРА_1,TELEGRAM_ID_МЕНЕДЖЕРА_2,TELEGRAM_ID_МЕНЕДЖЕРА_3
supabase secrets set APP_TIME_ZONE=Europe/Moscow
```

`TELEGRAM_MANAGER_IDS` — allowlist: только указанные ID могут включить менеджерские уведомления. Дополнительно разрешается аккаунт, который уже связан с записью `employees` с ролью `manager`. Не используйте примерные ID — подставьте реальные Telegram user ID.

### 3. Привяжите аккаунты сотрудников

Для каждого сотрудника заполните `employees.telegram_user_id` его реальным Telegram user ID. Это важно: бот не позволяет подавать заявки от имени произвольно выбранного сотрудника. Telegram user ID менеджеров также можно привязать к их существующим записям в `employees`.

### 4. Разверните функцию и установите webhook

```bash
supabase functions deploy shift-bot --no-verify-jwt
supabase secrets set SUPABASE_URL=https://ВАШ_PROJECT_REF.supabase.co
supabase secrets set SUPABASE_SERVICE_ROLE_KEY=ВАШ_SERVICE_ROLE_KEY
```

После деплоя установите webhook (замените значения на реальные):

```bash
curl -X POST "https://api.telegram.org/botВАШ_ТОКЕН/setWebhook" -d "url=https://ВАШ_PROJECT_REF.supabase.co/functions/v1/shift-bot"
```

Не публикуйте токен и `SERVICE_ROLE_KEY`. Они используются только на сервере.

### 5. Как пользоваться

- Каждый менеджер открывает бота, нажимает `/start`, затем **«Я менеджер»**. После проверки прав бот включает доставку личных уведомлений.
- Сотрудник открывает бота и нажимает **«Подать пожелания по сменам»**, выбирает дни, вводит интервалы (например `07:00-12:00, 14:00-18:00`), добавляет комментарий и подтверждает отправку.
- Бот сохраняет заявку в существующие `availability_requests` / `availability_intervals` и рассылает её подключённым менеджерам.
- Дедлайн рассчитывается на сервере в `APP_TIME_ZONE` (по умолчанию `Europe/Moscow`); после дедлайна бот показывает: «Свяжитесь с менеджером для составления графика».

Telegram не позволяет боту первым написать человеку: менеджер должен сначала открыть бота и нажать `/start`. Доставка требует правильного webhook, секретов Supabase, привязанных аккаунтов и применённой миграции. После настройки нужно проверить тестовую заявку в реальном Telegram.
